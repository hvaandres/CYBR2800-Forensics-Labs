Course: CYBR 2800

Lab Overview

In this lab, you will begin working as a Junior Digital Forensics Analyst. You will learn how forensic investigators acquire, preserve, verify, and begin analyzing digital evidence using open-source command-line tools.

This lab is designed around the terminal rather than graphical forensic applications. The goal is not simply to execute commands. You must understand what each command does, document your work, preserve evidence integrity, and explain how your findings support your conclusions.

Important: Digital forensics requires careful handling of evidence. Throughout this lab, assume that the evidence could be reviewed by another forensic investigator. Document your actions and do not make conclusions that are not supported by evidence.

Learning Objectives

After completing this lab, you should be able to:

  • Explain the purpose of digital evidence preservation.
  • Set up an Ubuntu-based forensic workstation.
  • Install and verify open-source command-line forensic tools.
  • Acquire a forensic image from an approved evidence source.
  • Calculate and verify SHA-256 hashes.
  • Identify partitions within a forensic image.
  • Identify the file system contained within a partition.
  • List files and directories using The Sleuth Kit.
  • Identify deleted files.
  • Extract selected files from a forensic image.
  • Document evidence using a basic chain-of-custody process.
  • Maintain professional forensic notes and documentation.

Investigation Scenario

You are working as a junior digital forensic investigator for a security team. Your organization has provided you with a computer image because the computer may have been involved in suspicious activity.

The security team believes the computer may have been used to:

  • Download suspicious files.
  • Access potentially malicious websites.
  • Create or modify unauthorized files.
  • Delete files after suspicious activity occurred.
  • Store information relevant to a security investigation.

Your initial responsibility is to answer the following question:

How can you acquire and preserve the evidence while demonstrating that the evidence has not been altered?

Later labs will build on the evidence you preserve during this investigation.

Evidence Source and Network Connectivity

The evidence for this lab is not distributed to you as a finished download. You will build it yourself in Part 4 by running a Python generator script published in the course GitHub repository. The script produces a 256 MB forensic disk image and its SHA-256 hash.

The generator runs on Linux only. It uses parted, losetup, mkfs.ext4, and loop mounting, and it must be run with sudo. Run it inside an Ubuntu virtual machine. It will fail on macOS, and you should not attempt to run it directly on your host operating system.

Because the evidence must be generated on a Linux machine, and because this lab requires you to acquire evidence from a source and transfer it to a separate analysis workstation, you must decide how the evidence will reach your Ubuntu forensic workstation before you begin Part 4.

Choose one of the three paths below and record your choice in your investigation notes. Every path requires the same hashing and verification work; only the transfer mechanism differs.

Path A: Two Virtual Machines Connected with Tailscale

Use two Ubuntu virtual machines. The first VM is the evidence host, where you run the generator and store the master image. The second VM is your forensic analysis workstation. You acquire the image on the evidence host and transfer it across the network to the analysis workstation.

Virtual machines using NAT networking usually cannot reach each other directly, and cloud VMs may sit behind firewalls that block inbound SSH. Tailscale creates a private network between your machines so scp works regardless of how they are hosted.

Install Tailscale on both virtual machines:

sudo apt update
sudo apt install curl

curl -fsSL https://tailscale.com/install.sh | sh

sudo tailscale up

Follow the authentication URL printed by tailscale up and sign in. Sign both machines in to the same Tailscale account, or they will not be able to see each other.

Confirm both machines are on the network:

tailscale status

tailscale ip -4

Record the Tailscale IP address (it will begin with 100.) of your analysis workstation. You will use it in Part 7.

Your analysis workstation must be running an SSH server to receive the file: 

sudo apt install openssh-server

sudo systemctl enable --now ssh

From the evidence host, verify connectivity before you acquire anything:

tailscale ping ANALYSIS_VM_TAILSCALE_IP

ssh USER@ANALYSIS_VM_TAILSCALE_IP

Path B: Physical Evidence Drive (USB or External Hard Drive)

Write the generated image onto a USB drive or external hard drive, then treat that physical device as the approved evidence source. You attach the device to your macOS or Windows computer, image it there, and move the resulting image to your Ubuntu workstation.

This path most closely matches real-world evidence handling and is the only path that exercises the diskutil and Get-Disk device-identification steps. It requires a spare drive you are willing to erase completely.

Path C: Single Machine (Evidence Stored Locally)

Generate the image and analyze it on the same Ubuntu virtual machine. No network transfer and no external drive are required. You still create a separate working copy of the image and verify its hash against the master, so the evidence-integrity portion of the lab is unchanged.

This is the simplest path and is fully acceptable for this assignment.

Important: The path you choose does not change your obligations. In all three paths you must record the hash of the source, hash your acquired copy, compare the two, and document every handling step in your chain of custody.

Important Safety and Evidence Rules

Follow these rules throughout the entire investigation.

  1. Do not image your personal computer. The only approved evidence source is the image you generate in Part 4. Never point an acquisition command at your own system disk.
  2. Do not modify the original evidence. Treat the original evidence as read-only.
  3. Do not execute suspicious programs. If you discover a suspicious executable, do not run it.
  4. Do not delete evidence. Preserve the evidence and document your actions.
  5. Do not guess device names. Always verify the device identifier before performing acquisition.
  6. Verify hashes. A transferred or acquired evidence image must be verified.
  7. Document errors. If a command fails, record the command, error message, and troubleshooting steps.
  8. Protect sensitive information. Do not publish or share personal information discovered in the evidence.

Part 3: Understand Digital Evidence Integrity

A forensic investigator must be able to demonstrate that evidence has not been unintentionally changed during acquisition, transfer, or analysis.

Cryptographic hashes provide a way to verify the integrity of files. In this lab, you will primarily use SHA-256.

For a file named evidence.dd, the command is:

sha256sum evidence.dd

The resulting hash should be recorded as part of your evidence documentation.

Evidence Preservation Rule: Never assume that two copies of an evidence image are identical. Calculate and compare their hashes.

Step 3: Build the Evidence Image

The script writes its output to the current working directory, so change into the directory where you want the evidence stored before running it. Keep this directory separate from ~/forensics/, which holds your analysis work. 

mkdir -p ~/evidence-source
cd ~/evidence-source

sudo python3 ~/CYBR2800-Forensics-Labs/hacking-thursdays/lab02/cybr2800_forensic_evidence.py

The script produces two files:

Your hash is unique to your build. Each run of the generator creates a new file-system UUID and new file timestamps, so your SHA-256 will not match another student's, and it will not match if you rebuild the image later. This is expected. The value that matters is the hash of your master image, which you will use to prove that your acquired copy is identical to your source. Record it in your investigation notes now, and do not rerun the generator after this point.

Step 4: Write the Evidence to a Physical Drive (Path B Only)

Skip this step if you selected Path A or Path C.

Identify your target drive carefully:

lsblk

Critical Warning: The next command erases the entire target device. Confirm the device name using its size in the lsblk output. Do not guess, and do not select the disk your operating system is installed on. 

sudo python3 cybr2800_forensic_evidence.py --write-to-device /dev/sdX

Replace /dev/sdX with your verified device. The script refuses to run unless the target is a real block device with enough capacity, and it prompts you to type YES before writing.

Shut down the VM or detach the drive, then connect it to your macOS or Windows computer and continue with Step 5.

Step 5: Identify the Evidence Device (Path B Only)

Skip this step if you selected Path A or Path C, and continue to Part 5.

macOS

List available disks:

diskutil list

Critical Warning: Do not blindly use an example such as /dev/disk4. Your computer may assign a different device identifier. This list also includes your Mac's own internal disk (usually containing "Macintosh HD"). Selecting the wrong device can permanently destroy your own data.

Expected macOS behavior: The evidence drive uses a Linux file system that macOS cannot read, so macOS will display a dialog stating the disk is not readable. Click Ignore. Do not click Initialize, which opens Disk Utility and can destroy the evidence.

Unmount the evidence drive before imaging it, so that macOS cannot write to it while you work. Unmounting the volumes leaves the device itself readable: 

diskutil unmountDisk /dev/diskN

Windows

Open PowerShell as Administrator and list available disks: 

Get-Disk

You can also review more detail, including partition layout and drive letters, using Disk Management: 

diskmgmt.msc

Critical Warning: Get-Disk lists every disk attached to your computer, including Disk 0, which is almost always your Windows system disk. Do not select your system disk. Confirm the evidence disk using its size before proceeding. Selecting the wrong disk number in later steps can permanently destroy your own data.

Carefully identify the evidence device by matching its size to the image you wrote in Step 4, regardless of which operating system you are using.

Record the following information in your investigation notes:

  • Device identifier (e.g., /dev/diskN on macOS or Disk N on Windows)
  • Device size
  • Device name
  • Date and time of acquisition
  • Your name

Part 5: Acquire the Evidence

The objective is to create a forensic working copy without modifying the original evidence. You will analyze the copy, never the master. The example output filename used throughout the remainder of this lab is: 

suspect.dd

Follow the subsection that matches the evidence path you selected.

Path A and Path C: Acquire on Linux with dc3dd

Your master image is a file on a Linux machine, so acquire your working copy with dc3dd. It hashes the data as it copies and writes its own acquisition log, which is exactly what a forensic acquisition tool is expected to do. 

cd ~/evidence-source

dc3dd if=CYBR2800_Lab1_Evidence.dd of=suspect.dd hash=sha256 log=acquisition.log

Review the log that dc3dd produced:

cat acquisition.log

The log records the input file, the output file, the number of sectors copied, and the SHA-256 hash of the data. Confirm that the hash in the log matches the hash in CYBR2800_Lab1_Evidence.dd.sha256 that you recorded in Part 4.

Why this matters: This comparison is the acquisition proof. It demonstrates that the working copy you are about to analyze contains exactly the same data as the source, and that your acquisition did not alter anything. If the two hashes differ, stop and repeat the acquisition before continuing.

Path B: macOS

dc3dd is a Linux tool and is not available on macOS. Acquire the image using the built-in dd command instead: 

sudo dd if=/dev/rSOURCE_DEVICE of=suspect.dd bs=4m 2> acquisition.log

Do not execute this command until you have confirmed the correct source device. Replace SOURCE_DEVICE with the device identifier provided for your lab (use the raw device, e.g. /dev/rdisk4, for faster imaging).

Path B: Windows

Windows does not include a built-in disk-imaging command. Use one of the following instructor-approved options:

  • FTK Imager (recommended): Use the free FTK Imager tool to create a raw (dd) image of the evidence disk. FTK Imager calculates the SHA-256 hash automatically and saves a verification report alongside the image.
  • WSL2 with a Linux tool: If approved by your instructor, attach the evidence device to WSL2 (e.g., using usbipd-win) and run the same dc3dd/dd commands shown for macOS/Linux from inside WSL2.

Whichever tool you use, save an acquisition log noting the tool and version used, the source device, the output filename, and the resulting hash.

When acquisition is complete, preserve the acquisition log.

Your acquisition directory should contain information similar to: 

acquisition/
└── acquisition.log

Part 6: Calculate the Evidence Hash

Calculate the SHA-256 hash of the forensic image you acquired.

Path A and Path C: Linux

cd ~/evidence-source

sha256sum suspect.dd

Compare it directly against the hash of the master image:

sha256sum suspect.dd CYBR2800_Lab1_Evidence.dd

The two hash values printed must be identical. Save the acquisition hash: 

mkdir -p ~/forensics/hashes

sha256sum suspect.dd > ~/forensics/hashes/evidence_sha256.txt

Path B: macOS

shasum -a 256 suspect.dd

Create a directory for your hashes on the Mac, then save the hash. The ~/forensics/ tree you created in Part 1 exists on your Ubuntu VM, not on your Mac, so you must create a local directory first: 

mkdir -p ~/forensics/hashes

shasum -a 256 suspect.dd > ~/forensics/hashes/evidence_sha256.txt

Path B: Windows

Using PowerShell:

Get-FileHash suspect.dd -Algorithm SHA256

Save the hash to a file:

Get-FileHash suspect.dd -Algorithm SHA256 | Out-File -Encoding utf8 evidence_sha256.txt

Note: The -Encoding utf8 option matters. Without it, Windows PowerShell writes the file in UTF-16, which appears corrupted when you open it on Ubuntu later.

If you used FTK Imager, you may instead use the hash value from its generated verification report.

Verify that the hash file contains the expected information: 

cat ~/forensics/hashes/evidence_sha256.txt

Part 7: Transfer the Evidence to Your Analysis Workstation

Move the forensic image and your acquisition documentation onto the Ubuntu forensic workstation. The forensic image belongs in ~/forensics/evidence/ and the acquisition documentation belongs in ~/forensics/logs/.

Follow the subsection that matches the evidence path you selected.

Path A: Transfer over Tailscale

Confirm your analysis workstation is reachable before transferring. From the evidence host: 

tailscale status

Copy the image and log using the Tailscale IP address or the Tailscale machine name of your analysis workstation: 

scp suspect.dd USER@ANALYSIS_VM_TAILSCALE_IP:~/forensics/evidence/
scp acquisition.log USER@ANALYSIS_VM_TAILSCALE_IP:~/forensics/logs/

If scp hangs or reports "Connection refused": the two machines are not connected. Verify that both appear in tailscale status and are signed in to the same account, that the analysis workstation is running ssh (sudo systemctl status ssh), and that you used the Tailscale address rather than a local 192.168.x.x address. Document this troubleshooting in your notes if it occurs.

Path B: Transfer with a Physical Drive

Copy suspect.dd and your acquisition log onto a separate USB drive from the one holding the evidence, then attach that drive to your Ubuntu VM. Do not write your working copy back onto the evidence drive.

On Ubuntu, identify and mount the transfer drive, then copy the files into place: 

lsblk

cp /media/$USER/YOUR_DRIVE/suspect.dd ~/forensics/evidence/
cp /media/$USER/YOUR_DRIVE/acquisition.log ~/forensics/logs/

Windows users may alternatively use a GUI tool such as WinSCP, or a shared folder configured in their virtualization software, instead of a second drive.

Path C: Local Copy

No network transfer is required. Copy the working image and acquisition log into your forensic workspace on the same machine: 

cp ~/evidence-source/suspect.dd ~/forensics/evidence/
cp ~/evidence-source/acquisition.log ~/forensics/logs/

Leave CYBR2800_Lab1_Evidence.dd in ~/evidence-source/. That file is your master evidence and must remain untouched.

Verify the Transfer

After transferring the evidence, calculate its SHA-256 hash again: 

cd ~/forensics/evidence

sha256sum suspect.dd

Compare this value with the hash generated during acquisition.

Part 8: Examine the Forensic Image

You will now begin analyzing the forensic image using The Sleuth Kit.

Step 1: Image Information

Step 2: Partition Analysis

Identify:

  • Partition scheme
  • Partition start sector
  • Partition size
  • Unallocated space
  • Potential file systems

Part 9: Analyze the File System

Using the partition offset identified in the previous step, run: 

fsstat -o YOUR_OFFSET ~/forensics/evidence/suspect.dd

Document:

  • File-system type
  • Block size
  • Volume information
  • File-system statistics
  • Other significant information

Part 10: List Files and Directories

List files in the file system:

fls -o YOUR_OFFSET ~/forensics/evidence/suspect.dd

Perform a recursive listing and save the results:

fls -r -o YOUR_OFFSET ~/forensics/evidence/suspect.dd > ~/forensics/case/files.txt

Review the output:

less ~/forensics/case/files.txt

Use command-line searches to identify potentially interesting information. 

grep -i "download" ~/forensics/case/files.txt

grep -i "\.exe" ~/forensics/case/files.txt

grep -i "password" ~/forensics/case/files.txt

Identify at least five files or directories that you believe may be relevant to the investigation.

Part 11: Investigate Deleted Files

Deleted files may continue to contain useful forensic information. Use The Sleuth Kit to identify deleted files.

Identify at least three deleted files.

For each deleted file, document:

  • Filename
  • Metadata address or inode
  • Original path, if available
  • File type
  • Why the file may be relevant

Part 12: Examine File Metadata

Select one interesting file and use istat to examine its file-system metadata. 

istat -o YOUR_OFFSET ~/forensics/evidence/suspect.dd INODE

Document:

  • File size
  • File type
  • Metadata address
  • Modified time
  • Access time
  • Change time

Part 13: Recover a Deleted File

Select one relevant deleted file and attempt to recover it using icat. 

mkdir -p ~/forensics/recovered

icat -o YOUR_OFFSET ~/forensics/evidence/suspect.dd INODE > ~/forensics/recovered/recovered_file

Identify the recovered file:

file ~/forensics/recovered/recovered_file

Calculate its SHA-256 hash:

sha256sum ~/forensics/recovered/recovered_file

Examine embedded metadata where applicable:

exiftool ~/forensics/recovered/recovered_file

Explain whether the file was successfully recovered and what information you were able to obtain from it.

Part 14: Generate a Basic File Timeline

The Sleuth Kit can be used to create a timeline of file-system activity.

Create a body file:

fls -r -m / -o YOUR_OFFSET ~/forensics/evidence/suspect.dd > ~/forensics/timelines/bodyfile.txt

Generate the timeline:

mactime -b ~/forensics/timelines/bodyfile.txt > ~/forensics/timelines/timeline.csv

Review the timeline:

less ~/forensics/timelines/timeline.csv

Identify at least 10 significant events.

Part 15: Search the Evidence

Use strings as an investigative tool. 

strings ~/forensics/evidence/suspect.dd | grep -i "http"

Try additional searches:

strings ~/forensics/evidence/suspect.dd | grep -i "password"

strings ~/forensics/evidence/suspect.dd | grep -i "username"

strings ~/forensics/evidence/suspect.dd | grep -i "download"

Forensic Interpretation: A string discovered using strings is not automatically proof that a user performed an action. Treat it as an investigative lead and attempt to validate the information using additional evidence.

Identify the recovered file types:

Identify files that may be relevant to the investigation.

Final Reminder

Digital forensics is not simply about finding suspicious files. A professional investigation requires you to:

  1. Preserve the evidence.
  2. Verify its integrity.
  3. Examine the evidence systematically.
  4. Document your actions.
  5. Analyze the information you discover.
  6. Support your conclusions with evidence.

If you encounter an error, do not simply skip the step. Capture the error, document what you attempted, and explain how you attempted to resolve it. Troubleshooting is part of working as a cybersecurity and digital forensics professional.
